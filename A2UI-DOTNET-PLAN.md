# A2UI Core and Agent SDK Plan for .NET

Research snapshot for 22 November 2026

## Recommended release strategy

Build two SDK packages for **A2UI protocol 1.0**. `A2UI.Core` provides the protocol and state engine. `A2UI.Agent` builds on it to generate and validate messages across turns. Start with a scripted form and verify its bidirectional messages against an upstream SDK using headless transcripts. Introduce model streaming after interoperability works. Keep SDK package versions independent of A2UI wire versions.

Upstream lists v1.0 as current, v0.9.1 and v0.9 as previous, and v0.8 as deprecated. Its official SDK inventory does not list first-party .NET packages. Shiny, Neuroglia, Syncfusion, and AG-UI provide reference implementations or integration examples. Implement the SDKs in this repository and use those projects to compare behavior. The clearest opportunity is a provider-neutral .NET Agent SDK with demonstrated 1.0 conformance. [Version registry](https://raw.githubusercontent.com/a2ui-project/a2ui/main/specification/versions.json) · [Official SDK inventory](https://a2ui.org/concepts/sdks/) · [Shiny release notes](https://shinylib.net/controls/release-notes/) · [Neuroglia source](https://github.com/neuroglia-io/a2ui-net) · [Syncfusion Core](https://www.nuget.org/packages/Syncfusion.A2UI.Core) · [AG-UI toolkit work](https://github.com/ag-ui-protocol/ag-ui/pull/2340)

| Release | Proposed scope | Evidence required |
| --- | --- | --- |
| Internal prototype | 1.0 wire codec, surface store, bindings, and a deterministic form | .NET and upstream SDKs agree on the scripted form's messages, state, and returned action |
| Public preview | 1.0 Core and Agent preview, Direct JSON batch and streaming, one sample transport | Applicable suites pass, and a clean package consumer runs the interop scenario |
| First stable SDK release | Complete declared 1.0 Core and Agent profile, including Express batch and streaming, Agent macros, trimming and Native AOT | Applicable upstream suites, interop, deployment checks and independent package installation pass |
| Compatibility and expansion | Optional catalog extensions, renderer framework adapters, additional transports and evaluation of v0.9.1 | Document the scope and fixtures for each integration. Identify a named consumer before adding a legacy wire version. |

Prioritize v0.9.1 compatibility if a first consumer requires it. Its schema already specifies `v0.9` and `v0.9.1` as accepted version strings, uses canonical schema IDs under `v0_9`, and requires a surface catalog ID. The remaining decision is whether and when to implement that adapter and which accepted version to emit to a particular peer. [v0.9.1 wire schema](https://github.com/a2ui-project/a2ui/blob/main/specification/v0_9_1/json/server_to_client.json) · [v0.9.1 protocol](https://a2ui.org/specification/v0.9.1-a2ui/)

## Behavior established upstream

| Area | Implementation contract |
| --- | --- |
| Wire and session ordering | The 1.0 envelope declares `"version": "1.0"` and one message kind. Apply envelopes in arrival order, create a surface before updating it, reject duplicate live IDs, and apply inline initial data before resolving inline components. The implicit `Surface` container points to the component with ID `root`. Earlier mutations take effect before an RPC dispatch, and async execution can complete later. [Wire schema](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/json/agent_to_renderer.json) · [Protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md) |
| Validation and progressive updates | Validate a candidate graph formed by merging a batch with current state before committing. Check schema, duplicate IDs, composition and topology under the configured validation policy. Upstream defines strict checks and progressive handling of missing roots and forward references. Use its fixtures to identify the precise points where a pending reference becomes an error. [Core blueprint](https://github.com/a2ui-project/a2ui/blob/main/blueprints/modules/a2ui_core.blueprint.md) · [Conformance guide](https://github.com/a2ui-project/a2ui/blob/main/conformance/README.md) |
| Catalog lookup and references | Resolve each component or function in its explicit catalog, then the surface default if omitted. Report an error if neither supplies a valid catalog. Cache a validator per catalog and bind documented relative schema references in an offline registry. [Core blueprint](https://github.com/a2ui-project/a2ui/blob/main/blueprints/modules/a2ui_core.blueprint.md) |
| Data model and expressions | An omitted or `/` update path targets the root. Null deletes a member and resets the root to an empty object. The data model owns its stored values. Follow the prescribed expression and coercion rules, UAX #31 identifiers, and A2UI regex subset and safety checks. Use conformance cases for numeric, Unicode, formatting, and nested-scope edge cases. [Core blueprint](https://github.com/a2ui-project/a2ui/blob/main/blueprints/modules/a2ui_core.blueprint.md) |
| RPC and data sync | Enforce catalog caller and user-activation rules, correlate replies by call ID, and use upstream cases for pending checks, cancellation, and reactive call sharing. Imperative actions invoke each time. When `sendDataModel` is enabled, attach the snapshot to outgoing traffic for the owning agent. Passive edits alone do not send it. [Protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md) · [Core function routing cases](https://github.com/a2ui-project/a2ui/blob/main/conformance/README.md) |
| Agent negotiation and inference | Reuse the negotiated catalogs for prompt generation and stateful outbound validation. Use the Direct JSON streaming suite for emission boundaries, partial results, malformed blocks, and finalization. Start Express with batch compile and decompile. Confirm streaming support against the pinned revision before claiming it, since upstream descriptions differ. [Agent blueprint](https://github.com/a2ui-project/a2ui/blob/main/blueprints/modules/a2ui_agent.blueprint.md) · [Conformance guide](https://github.com/a2ui-project/a2ui/blob/main/conformance/README.md) |

## Package boundaries and public API

| Proposed package | Owns | Consumer entry point |
| --- | --- | --- |
| `A2UI.Core` | Wire messages, codecs, protocol adapters, catalog schema and conformance validation, session state, data and expression resolution, node changes, action and function contracts | Create an `A2uiSession`, apply a wire message, read a surface snapshot, observe changes or outbound messages |
| `A2UI.Agent` | Capability negotiation, catalog providers and filtering, prompt and skill generation, inference formats, response streaming, outbound validation, agent function dispatch | Create a generator and request processor, start a response stream, feed model output, receive typed text and validated A2UI parts |

Names and API signatures are provisional. Agent depends directly on Core. Keep schema assets and portable functions available to both packages. Evaluate a separate Basic Catalog or transport package when a consumer demonstrates a separate dependency or release need.

Keep package projects under `src/`, Core and Agent conformance harnesses under `tests/`, and headless replay and ASP.NET Core samples under `samples/`. Record fixture provenance in one manifest.

## Dependencies, .NET compatibility and performance

- **Dependencies.** Prefer the .NET base class library and implement A2UI-specific functionality in-house. A third-party library may be added to an SDK only when a measurement shows a clear benefit over the in-house or base class option. It must be MIT-licensed and support trimming and Native AOT in a clean consumer. Verify the license of the exact shipped version and its transitive library dependencies. Treat upstream protocol schemas and conformance fixtures as reference or test assets and preserve their published licenses and notices if redistributed.
- **Target frameworks.** Attempt a shared `net8.0` baseline for both packages and test clean consumers running on .NET 8, 9, 10 and 11. A compatible baseline assembly can serve newer .NET versions. If .NET 8 requires substantial workarounds or blocks a required API or acceptable performance, move the baseline to `net9.0` and verify .NET 9, 10 and 11. Add a separate newer target only where measurements or API requirements justify it. Microsoft ended servicing for .NET 8 and 9 on 10 November 2026. List SDK compatibility separately from Microsoft's runtime support, and use .NET 10 or 11 for deployment examples. [NuGet compatibility rules](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/nuget-package-compatibility-rules) · [Microsoft .NET lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/microsoft-net-and-net-core)
- **Performance.** Run upstream Core and Agent scaling cases for graph updates and inference parsing in a dedicated warmed-up Release job. Benchmark bytes and messages per second, allocated bytes, first-message latency, and repeated small updates on representative surfaces. Track baselines on the oldest supported runtime and a current runtime. Prefer incremental work, reuse compiled catalog validators, and test the cost of copying JSON and notifying subscribers. Profile before introducing pooling, specialized parsing, or runtime-specific paths, and retain an optimization when it makes a reproducible difference and keeps behavior and ownership clear. [Upstream performance suites](https://github.com/a2ui-project/a2ui/blob/main/conformance/README.md#timing-cases)

## Phase 0 — Baseline and feasibility

1. Pin an A2UI commit and record the corresponding schema, catalog, blueprint, fixture and reference SDK revisions. Vendor or fetch assets reproducibly with SHA and license information. Maintain a capability matrix by protocol and package.
2. Compile a minimal Core and Agent spike against `net8.0` and run clean consumer apps on .NET 8 through 11. Check the required APIs and any dependencies, then evaluate `net9.0` as the fallback if needed. Verify NuGet name availability.
3. Prototype `System.Text.Json` wire handling with source-generated metadata and owned JSON values. Compare a small implementation for A2UI's documented schema profile with an MIT-licensed Draft 2020-12 validator, if a candidate satisfies the dependency policy. Exercise mixed catalogs, offline references, diagnostics, and a trimmed headless consumer before committing a public API.
4. Capture an upstream transcript with capabilities, incremental updates and a returned action. Use it to build a headless harness and record initial performance measurements for the first cross-language milestone.

**Exit:** A pinned baseline, a verified framework floor, a JSON/schema validation decision, and a runnable headless harness with initial measurements.

## Phase 1 — Core SDK

1. Implement version-aware codecs for the two message directions and transport metadata. Model envelopes as typed alternatives and distinguish absent fields, explicit null and unresolved values. Reject malformed envelopes per schema, preserve supported extension data, and route version-specific operations through a shared engine. Keep JSONL, SSE and provider chunk framing outside wire-message decoding.
2. Implement a per-session surface store with ordered mutations, a canonical root, catalog resolution and version-correct create, update and delete. Validate per-item shape and merged graph topology before committing mutations where required. Cover placement constraints, cycles, duplicate IDs, staged references, reachability, mixed catalogs and validation policies. Publish coherent snapshots or change sets after commit. Make subscriber reentrancy, cancellation and disposal explicit.
3. Implement root replacement and pointer-based writes, escaped keys, array behavior, scope resolution for nested templates and local write-back. Add dependency tracking and resolved nodes with stable occurrence identity. Drive checks and side-effect-free catalog functions from this engine. Test coercion, formatting, interpolation, numeric and Unicode behavior against upstream fixtures before reusing .NET defaults.
4. Implement events, structured errors, capabilities and owner-scoped data sync. Add both v1.0 function RPC directions in the declared profile, with catalog permission and user-activation checks, correlation and cancellation. Match upstream semantics for pending checks, reactive call sharing and caching, and fresh imperative action calls. Drop late responses after deletion or session disposal. Group replies around one ordered outbound abstraction. [v1.0 wire and function contracts](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md) · [Core blueprint](https://github.com/a2ui-project/a2ui/blob/main/blueprints/modules/a2ui_core.blueprint.md)

**Exit:** A headless session processes the pinned golden examples. Applicable Core suites for lifecycle, schema, graph integrity, state, expressions, actions and RPC run through public entry points. A failed atomic operation leaves the previous valid snapshot intact. Scaling tests cover updates arriving in many small frames.

## Phase 2 — Agent SDK

1. Read versioned renderer capability metadata and resolve the intersection of supported versions and catalogs. Support fixed catalogs and negotiated catalogs, including validated inline catalogs under explicit policy. Use the same catalog set for prompt generation and validation. Support pruning components and functions and generating prompt instructions, examples and skill documents.
2. Implement Direct JSON batch compilation, decompilation, response framing and streaming. Keep plain text and A2UI parts ordered. Handle arbitrary chunk boundaries, escaped characters, truncated streams, malformed and unsupported content, cancellation and size limits. Use upstream cases to define eligible incremental emission. Track the renderer's state across turns and preserve the distinction between accepted operations and already-emitted messages. Once a message is delivered, recovery uses ordered updates or a defined resync policy.
3. Support deterministic messages through the same validation path. Route incoming actions, metadata, errors and RPC through host callbacks. Leave model retries, state durability and business-side effects under application control. Use a scripted provider for CI, then demonstrate one adapter based on `Microsoft.Extensions.AI` or a comparable host abstraction if the first integration needs it.
4. Add Express after Direct JSON interop is stable. Implement the pinned grammar, batch compiler, decompiler, prompt generation and incremental streaming. Round-trip the Basic Catalog corpus and compare normalized output, diagnostics and message order with upstream. Implement catalog-aware macros and verify the v1.0 expansion corpus. [Agent blueprint](https://github.com/a2ui-project/a2ui/blob/main/blueprints/modules/a2ui_agent.blueprint.md) · [Agent implementation guide](https://github.com/a2ui-project/a2ui/blob/main/python/a2ui_agent/agent_development.md)

**Exit:** The SDK can generate a deterministic form and compile a streamed model response, validate through Core, and process the form's returned action in the next turn. The public compatibility matrix lists inference formats by version and identifies intentional gaps.

## Phase 3 — Integration and release verification

- **Conformance.** Use the upstream module blueprints as the SDK implementation reference and pin them with the protocol schemas and both official test suites. Load the upstream Core and Agent YAML cases in the test harness and exercise the public SDK entry points. Require all applicable cases to pass for release. Report passes, failures and the reason for each scope exclusion by suite and version. Preserve expected diagnostics and outputs. Include the generated-schema comparison where claiming that capability. Re-run the same matrix when upstream advances. [Module blueprints](https://github.com/a2ui-project/a2ui/tree/main/blueprints/modules) · [Core suite](https://github.com/a2ui-project/a2ui/tree/main/conformance/core) · [Agent suite](https://github.com/a2ui-project/a2ui/tree/main/conformance/agent) · [Harness implementation guide](https://github.com/a2ui-project/a2ui/blob/main/conformance/conformance_harness_implementation_guide.md)
- **Interoperability.** Pass .NET Agent output into a pinned upstream Core SDK and replay Python or TypeScript Agent output through .NET Core. Compare progressive updates, local edits, actions and context values, data sync, function success and errors, and deletion. Run the scenario from clean NuGet consumers on each claimed runtime.
- **Transport sample.** Use typed in-process messages in the primary walkthrough. Provide an ASP.NET Core reference sample with an ordered SSE stream and a POST return channel. Define versioned metadata placement, cancellation and reconnect behavior for that sample. Add AG-UI, A2A or MCP bindings as opt-in integrations after confirming their audience and protocol support. [Protocol transport bindings](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md)
- **Trust boundaries.** Use registered catalog definitions and host functions, validate inline catalogs against policy, and resolve schema references from a controlled registry. Enforce per-session surface ownership and agent/renderer caller permissions. Delegate external URLs and media to host policy, treat link activation as explicit user input, and validate actions before invoking business operations. Keep payload values out of telemetry by default. Bound message bytes, graph depth and size, expression cost, pending calls and cache memory.
- **CI and publishing.** Test Core and Agent on headless .NET runners with trim and AOT analysis enabled. Verify both trimmed and Native AOT publish and execution in clean package consumers for each declared deployment target. Test `dotnet pack`, installation from a local feed, API compatibility, package metadata, license and notices, Source Link, symbols, docs and release notes. Publish supported versions and conformance results against the pinned upstream revision. [Upstream community criteria](https://a2ui.org/reference/renderers/)

## First implementation milestone

Deliver a two-turn appointment form using a small shared catalog. The .NET agent creates a surface, sends a component update that adds a check, and sends an independent data update. An upstream Core test client applies a scripted local edit and emits the submit action. The .NET agent confirms the submission and deletes the surface on a scripted close. Replay equivalent upstream Agent output through .NET Core. Assert resolved values, outbound actions and final disposal, including a templated list reorder case.

Use a one- to two-week Phase 0 timebox for one experienced engineer. Re-estimate after the framework and validation spikes, headless publish, and cross-language round trip. Estimate Express and production transport integrations separately.
